\section*{Summary}\addcontentsline{toc}{section}{Summary}
\begin{itemize}
  \item All 20,000 orders are kept: 16,482 get a reliable label, the rest a reason why not. A value is fixed only when an independent record (a \emph{witness}) shows the true value.
  \item 6.7\% of labelled orders are late (95\% interval 6.3--7.1\%). Lateness comes in waves, short estimates are late twice as often, and RJ adds the most late deliveries.
  \item 16,482 $\times$ 72 numeric features, only from what is known at approval. One command rebuilds and checks every output.
\end{itemize}

\textbf{Key decisions.}
\begin{center}\small
\begin{tabular}{lll}
\toprule
decision & instead of & because \\
\midrule
SQL in SQLite via ADBC & pandas, DuckDB, Polars & least memory at every scale (\S1) \\
Parquet with zstd & CSV, snappy, gzip & smallest at the same speed, keeps types (\S1) \\

\section{Loading the data}

\begin{center}\small
\begin{tabular}{llll}
\toprule
table & rows & key & one row is \\
\midrule
orders & 20,000 & order\_id & an order (the grain) \\
customers & 20,000 & customer\_id & the customer record of one order \\
order\_items & 22,662 & order\_id + order\_item\_id & one item (2 of a product = 2 rows) \\
order\_payments & 20,875 & order\_id + payment\_sequential & one payment, in centavos \\
order\_reviews & 19,966 & review\_id + order\_id & one review \\
products / sellers & 11,334 / 2,071 & product\_id / seller\_id & catalogue rows \\
\bottomrule
\end{tabular}
\end{center}

\textbf{One row per order.}
\begin{itemize}
  \item Items, payments and reviews are one-to-many. Joined raw, 3 items $\times$ 2 payments = 6 rows and double-counted totals.
  \item So \file{sql/orders.sql} aggregates each per order inside SQLite, then left joins onto orders. No fan-out, no order lost. Payments stay in integer centavos, so totals are exact.
  \item \file{EXPLAIN QUERY PLAN}~\cite{eqp}: each GROUP BY walks the \file{order\_id} index.
\end{itemize}

\textbf{Relationships and totals preserved} (\file{key\_links.csv}, \file{checks.csv}).
\begin{itemize}
  \item 0 items, payments or reviews point to a missing order.
  \item Gaps the other way stay as NULLs: 769 orders have no customer row, 142 have no items, 910 items have no product row and 893 have no seller row.
  \item 0 duplicate orders, 0 customer records shared by two orders; the 998 repeated item rows are quantity. Counts and totals (price total 54,446,205.77, payment total 280,524,473 centavos) are equal in the database and the output.
\end{itemize}

\textbf{Why this is the most efficient choice.} The same table built 8 ways at 1$\times$, 3$\times$ and 10$\times$ the data, each in a fresh process, median of 3 (\file{bench.py}).

\begin{figure}[htbp]\centering
\includegraphics[width=0.78\linewidth]{01_load/engine_comparison.png}
\caption{At 10$\times$ the data, SQLite SQL through ADBC needs the least memory. DuckDB is fastest but needs 2.4--4$\times$ the memory.}
\end{figure}

\begin{itemize}
  \item \textbf{My first estimate was wrong.} With Python's \file{sqlite3} driver, SQL needed as much as pandas (421 vs 406 MB): it builds a Python object per value, 20 MB of objects for a result that is 7 MB as a dataframe. ADBC hands over Arrow columns~\cite{adbc}, and SQL then needs under a third of pandas' memory (120 vs 406 MB).
  \item \textbf{DuckDB}~\cite{duckdb} is 5--13$\times$ faster but holds 290--480 MB for its join hash tables. Writing to a file did not help; a memory cap made the query fail.
  \item \textbf{Polars} (lab 7), streaming~\cite{polars}: the most memory (606 MB). Streaming helps when inputs do not fit in memory; here they do.
  \item \textbf{Decision:} no engine wins on both. Memory decides whether a step fits at all; 1.7 s at 10$\times$ is fine for a batch step.
  \item \textbf{Storage:} Parquet keeps types that CSV turns into text~\cite{parquet}. Orders: CSV 5.25 MB, Parquet uncompressed 4.66, snappy 3.29, gzip 2.15, zstd 2.08. zstd is smallest at snappy's speed, so all outputs use it (\file{storage.csv}).
\end{itemize}

\section{Data quality and cleaning}

\textbf{Rule, strongest first.} \textbf{Fix} only with a witness; else \textbf{set missing}; \textbf{flag} fields that feed neither labels nor features. No order is deleted. Every change is logged with key, column, rule, old and new value (\file{changes.parquet}).

\begin{center}\small
\begin{tabular}{lrl}
\toprule
problem & values & action \\
\midrule
negative price / freight & 408 / 458 & absolute value \\
price $>$ 5,000 / freight $>$ 500 & 417 / 473 & divide by 1,000 \\
size $>$ 200 cm or weight $>$ 100 kg & 783 items & missing \\
$-1$ photos, name or description length & 690 items & missing \\
state ZZ or blank & 838 orders, 1,031 items & missing, then recovered from zip \\
impossible date, size $\le 0$, placeholder category & see \file{profile.csv} & missing \\
status with spaces or capitals & 783 & strip, lowercase \\
\bottomrule
\end{tabular}
\end{center}

\textbf{Why these fixes are trusted.}
\begin{itemize}
  \item \textbf{Prices.} The payment is a witness. After the fix, price + freight matches the payment for 87\% / 90\% (negative) and 94\% / 88\% (large) of orders, the same as clean orders (90\%). Dividing by 100 matches 0\%. A second witness: the same product sells elsewhere at the fixed price for 178 of 277.
  \item \textbf{Sizes.} Freight says the values are wrong: ``over 100 kg'' items ship for R\$15.2, like 0.4--1.4 kg items (R\$16.1), not 20--30 kg ones (R\$74.6). But freight cannot give the exact value, so missing, not divided.
  \item \textbf{States.} A zip prefix sits in one state, so missing states come back from the zip (895 customers, 1,032 sellers). 14 prefixes with two states are not used. Recovered rows are flagged.
\end{itemize}

\textbf{Labels.} \file{delivered\_after\_estimate} = 1 if delivered after the estimated calendar date, 0 if on or before it (local clock). Only usable completed deliveries are labelled.

\begin{figure}[htbp]\centering
\includegraphics[width=0.6\linewidth]{02_clean/record_accounting.png}
\caption{Every order is labelled or has one reason why not.}
\end{figure}

\textbf{Unresolved, and what it affects.}
\begin{itemize}
  \item Price + freight now matches the payment for 16,302 of 18,122 complete orders (14,845 before). Of the 1,820 left, 919 have a negative payment and 832 paid exactly R\$7.23 more.
  \item \textbf{R\$7.23 extra} on 832 orders: same payment types, states and months as all orders (credit card 76\% vs 72\%, SP 40\% vs 42\%). Spread evenly, so it cannot bias a comparison.
  \item \textbf{Payments} (negative values, 929 instalments of $-1$) are left: they are only a witness. 0 instalments is valid.
  \item \textbf{Carrier pickup before approval} (270): flagged; the carrier date is not used.
  \item \textbf{\file{not\_reported}} (804) and deliveries dated exactly 7 days before approval (782 of 791 too early): unlabelled, since a fix would be a guess. Section 3 puts them back as a test.
  \item \textbf{Extreme delays} (up to 188 days, 14 orders over 60): kept, their dates are consistent.
  \item A missing optional catalogue field (price, size, category) never removes an order: it stays missing and the order keeps its label.
\end{itemize}

\section{Exploratory analysis}

\textbf{Why every rate has an interval, and why Wilson.}
\begin{itemize}
  \item Groups range from 8 orders (AP) to 6,523 (SP), so a rate alone hides how much to trust it. Every rate gets a 95\% interval.
  \item The textbook interval $p \pm 1.96\sqrt{p(1-p)/n}$ breaks for small groups and rates near 0: 0 late out of 8 gives 0--0\%, as if 8 orders proved a state is never late. Brown, Cai and DasGupta show its coverage is erratic and that the usual rules for when it is safe are misleading~\cite{brown}.
  \item Wilson's interval~\cite{wilson} comes from the score test, stays inside 0--100\% and stays sensible at 0 or all late: 0 out of 8 gives 0--32\%. Brown et al.\ recommend it (or Jeffreys) for small samples; for large groups the common methods give nearly the same interval, so one method serves every group.
\end{itemize}

\subsection{Q1. How often are orders late, and by how much?}
\begin{itemize}
  \item 6.7\% of labelled orders are late (6.3--7.1\%), about 1 in 15.
  \item A late order is typically a week late (median 7 days, middle half 3--13); 1 in 8 is 3+ weeks late.
  \item The typical on-time order arrives 13 days early: estimates are padded.
\end{itemize}
\begin{figure}[htbp]\centering
\includegraphics[width=0.49\linewidth]{03_eda/q1_days_vs_estimate.png}\hfill
\includegraphics[width=0.49\linewidth]{03_eda/q1_late_by_month.png}
\caption{Lateness comes in waves, with 18\% of March 2018 orders late against 1--8\% in normal months.}
\end{figure}

\subsection{Q2. Time from approval to the estimate}
\begin{itemize}
  \item Estimates under a week are late 16\% of the time, twice any other group. From 1 to 5 weeks it is 5--7\%; beyond 6 weeks, under 2\%.
  \item \textbf{Not state or season:} no short estimate falls in the spike months, and within the same state and month, short estimates are late 16.3\% vs 4.2\%.
  \item An association, not a cause, but a short estimate is a useful risk signal at approval.
\end{itemize}
\begin{figure}[htbp]\centering
\includegraphics[width=0.75\linewidth]{03_eda/q2_late_by_lead_time.png}
\caption{Short estimates are late twice as often, also within the same state and month.}
\end{figure}

\subsection{Q3. Which states, and where to look first?}
\begin{itemize}
  \item Ranked by \textbf{excess late orders} = late orders $-$ orders $\times$ overall rate: the late deliveries a state adds. A high rate on 9 orders is mostly noise; a slightly raised rate on 2,000 orders is many late deliveries.
  \item \textbf{RJ first} (+98), then BA (+26) and CE (+22). RJ's rate (11.5\%) is not the highest, but it is on 2,036 orders.
  \item \textbf{Drill-down:} 65 of RJ's excess falls in the spike months and 94 is on sellers in SP. Start with the SP $\to$ RJ route at peak times. BA's excess is mostly outside the spikes: a steady problem.
  \item RR (9 orders) and AP (8) are too small. By chance 1--2 of 27 states would sit outside the overall rate; 12 do, so states really differ.
  \item 951 labelled orders (6\%) have no state, 741 of them because the customer row is missing.
\end{itemize}

\includegraphics[width=0.52\linewidth]{03_eda/q3_late_by_state.png}\hfill
\includegraphics[width=0.47\linewidth]{03_eda/q3_drilldown.png}
\caption{RJ adds the most late deliveries, mostly in the spike months and on sellers in SP.}
\end{figure}

\subsection{Data quality, sensitivity and confidence}
\begin{itemize}
  \item Changing each cleaning choice keeps the late rate at 6.4--6.8\%, and the top 3 states are always RJ, BA and CE.
  \item The real gap is coverage: 18\% of orders have no label. The 944 cancelled orders could move the late rate from 6.4\% (none late) to 11.8\% (all late); 743 of them were already with the carrier, so 6.7\% is best read as a lower bound.
  \item This is one modified extract (2016--2018): these are where to look first, not proven causes.
\end{itemize}

\section{Feature engineering}

One row per labelled order (16,482). Columns not available at approval (payments, status, carrier and delivery dates, reviews, \file{shipping\_limit\_date}) are dropped \emph{before} building, so using one by mistake fails. IDs and labels sit in \file{ids\_labels.parquet}, same row order.

\begin{center}\small
\begin{tabular}{lp{9.5cm}r}
\toprule
group & features & columns \\
\midrule
timing & days approval to estimate, hours purchase to approval, purchase month / weekday / hour as sin + cos & 8 \\
basket & items, products, sellers, price total, freight total, freight share & 6 \\
product / seller & weight, volume, photos, seller states, share from the customer's state & 5 \\
missing flags & one per feature that can be missing & 8 \\
customer state & one-hot, 27 states + missing & 28 \\
category & most expensive item, top 15 + other + missing & 17 \\
\bottomrule
\end{tabular}
\end{center}

\begin{itemize}
  \item \textbf{Representation.} Sums per order, set to missing if a part is missing. Missing stays NaN with a flag; imputing here would use future test orders, and imputation must be learned from training data only~\cite{pitfalls}. Cyclic time as sin + cos, so December sits next to January~\cite{cyclic}; no year. Rare categories grouped as ``other''.
  \item \textbf{Kept.} Two copies dropped: \file{est\_days\_from\_purchase} (= lead days + approval hours / 24) and \file{n\_categories} (= not category missing). The highest remaining correlation is 0.78 (weight vs volume). Each feature's meaning and source columns: \file{feature\_descriptions.csv}.
  \item \textbf{No leakage.} No source column is forbidden (checked in code). Each feature alone scores an AUC of 0.43--0.61, while the outcome \file{days\_late} as a control gets 1.0.
  \item \textbf{Reliability.} A check model, run after step 4's resource numbers: a gradient-boosted tree~\cite{sklearn}, which handles NaN itself~\cite{hgb}, trained on all orders before a cutoff and tested on the months after~\cite{tscv}, at three cutoffs (February, April, June 2018). All features score 0.58--0.62 every time, each 95\% bootstrap interval~\cite{efron} above 0.5. Lead time alone scores 0.45--0.53, and the leak control 1.0. Modest but real signal, and no leak.
\end{itemize}

\section{Reproducibility and resources}

\textbf{One command, strict checks.} \file{run.py} (with uv, or pip and \file{requirements.txt}) stops unless:
\begin{enumerate}[leftmargin=1.5em]
  \item Python is 3.12 and the supplied files match their SHA-256 hashes;
  \item \file{data/} is rebuilt from nothing, so no earlier output survives;
  \item every notebook assert passes, and every cell runs once, in order, with no error;
  \item every output matches \file{expected.sha256} byte for byte.
\end{enumerate}
A fresh clone and a clean Linux container without uv both pass. Every SQL query run is saved to \file{executed\_sql.sql}. Environment: Python 3.12, pandas 3.0, pyarrow 26.

\textbf{Estimated vs measured.} Saved storage is the Parquet and CSV files a step writes; they are also the intermediate data the next step reads. Memory is peak RSS above the step's start, sampled every 10 ms; it moves between runs, so the table shows the range over 5 runs. Estimates from each step's in-memory data: memory 2--3$\times$; zstd Parquet 0.2--0.35$\times$ of the tables written.

\begin{itemize}
  \item Steps 2--4 land on or near their memory estimates (no run more than 20\% outside). Step 1 needs about twice its estimate, likely Arrow buffers held before pandas wraps them (not measured separately).
  \item Saved storage lands inside the estimate for steps 0--2. Step 4 saved 0.9 MB against 2.1--3.7: one-hot zeros compress far better than the rule assumes. Temporary storage is 298 MB, only for the 10$\times$ engine comparison, then deleted.
  \item \textbf{Step 0 was the big miss} (205 vs 33--52 MB). The reviews contain emoji, and one character above U+FFFF makes Python store the whole 18-million-character text at 4 bytes per character (73 MB)~\cite{pep393}. Measured: reading as bytes peaks at 33 MB, decoding at 123 MB, and reading as text (what \file{setup\_db.py} does) at 196 MB. The loader is supplied, so it stays.
\end{itemize}

\textbf{Limitations.} Findings describe this modified extract; associations are not causes. 18\% of orders are unlabelled, so the late rate is a lower bound.
